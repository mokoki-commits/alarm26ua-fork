Проект родился из двух рабочих скриптов okova (`alarm.py` и `on.py`). Идея
(сигнализировать импульсами реле о тревоге и отбое по данным API, с разными
паттернами для разных типов тревог) принадлежит okova. Claude провёл аудит этих
скриптов и собрал из них постоянно работающий сервис с защитой от зависаний и
перерасхода памяти, запускаемый из venv под systemd.

## Назначение

Сервис раз в `POLL_INTERVAL` секунд опрашивает API ukrainealarm для заданного
региона и управляет реле Tuya (по локальной сети, через `tinytuya`):

- при **начале тревоги** — запускает паттерн импульсов, выбранный по типу тревоги;
- при **смене типа** тревоги (например, жёлтая → оранжевая, красная → просто
  воздушная и в любую другую сторону) — запускает паттерн нового типа;
- при **отбое** — запускает паттерн отбоя.

Конфигов ровно два: `config.txt` и `snapshot.json`. Файл `devices.json` не используется.

## Как это работает

Режимы запуска `alarm.py`:

```
alarm.py          сервис (опрос API, паттерны)
alarm.py on|off   включить / выключить реле (читает snapshot.json)
alarm.py check    диагностика: tinytuya, snapshot.json, выбор реле (реле не трогает)
```

Логика состояний:

| Было | Пришло от API | Действие |
|---|---|---|
| спокойно | тревога | паттерн типа тревоги |
| тревога (тип A) | тревога (тип B) | паттерн типа B |
| тревога | спокойно | `PATTERN_CLEAR` |
| нет сохранённого состояния | любое | ничего, только запоминаем |
| ошибка запроса | — | пропуск, повтор с нарастающей паузой (до 5 мин) |

Типы воздушной тревоги определяются по уровню: `AIR_RED`, `AIR_ORANGE`,
`AIR_YELLOW`; воздушная без определённого уровня — `AIR`. Остальные типы:
`URBAN_FIGHTS`, `ARTILLERY`, `NUCLEAR`, `CHEMICAL`, `UNKNOWN`.

Если активно несколько типов, выбирается самый приоритетный:
`URBAN_FIGHTS` › `ARTILLERY` › `NUCLEAR` › `CHEMICAL` › `AIR_RED` ›
`AIR_ORANGE` › `AIR_YELLOW` › `AIR` › `UNKNOWN`. Для типа без своего паттерна
используется `PATTERN_DEFAULT`.

Состояние (тревога/спокойно и последний тип) сохраняется в
`/var/lib/alarm/state.json`. После перезапуска сервиса или сервера, если с
последнего опроса прошло не больше `STATE_MAX_AGE`, изменения, случившиеся за
время простоя, отрабатываются (в том числе отбой).

## Установка

```bash
# в каталоге с файлами проекта; положите рядом свой snapshot.json
sudo bash install.sh
sudoedit /opt/alarm/config.txt          # API_KEY, REGION_ID, паттерны
sudo /opt/alarm/venv/bin/python /opt/alarm/alarm.py check
sudo systemctl restart alarm
journalctl -fu alarm
```

`install.sh` создаёт системного пользователя `alarm`, каталог `/opt/alarm`,
venv `/opt/alarm/venv`, ставит зависимости и регистрирует `alarm.service`.
Код и venv принадлежат root: сервис не может их изменить. Существующий
`config.txt` повторный запуск не затирает.

Нужны: Linux с systemd, Python 3.9+, пакет `python3-venv` (на Debian/Ubuntu:
`sudo apt install python3-venv`).

## Конфигурация (`config.txt`)

Формат `КЛЮЧ=значение`, строки с `#` — комментарии.

**Обязательные**

| Параметр | Описание |
|---|---|
| `API_KEY` | Ключ API ukrainealarm |
| `REGION_ID` | Идентификатор региона |
| `CMD_ON`, `CMD_OFF` | Команды включения/выключения реле (через shell). Для встроенного управления: `/opt/alarm/venv/bin/python /opt/alarm/alarm.py on` и `... off` |
| `PATTERN_CLEAR` | Паттерн отбоя |

**Паттерны** — `первый_вкл,последующие_вкл,пауза,количество` (секунды):
`PATTERN_DEFAULT` (по умолчанию `5,3,5,2`) и `PATTERN_<ТИП>`, например
`PATTERN_AIR_RED`, `PATTERN_AIR_ORANGE`, `PATTERN_AIR_YELLOW`, `PATTERN_AIR`,
`PATTERN_ARTILLERY`.

**Необязательные** (значение по умолчанию → допустимый диапазон)

| Параметр | По умолч. | Описание |
|---|---|---|
| `POLL_INTERVAL` | 65 (30–3600) | Период опроса, сек |
| `TUYA_DEVICE_ID` | — | ID реле; обязателен, если в `snapshot.json` больше одного устройства |
| `TUYA_VERSION` | из snapshot / 3.4 | Версия протокола Tuya |
| `HTTP_TIMEOUT` | 10 (1–60) | Таймаут сокета на запрос, сек |
| `HTTP_DEADLINE` | 30 (5–120) | Жёсткий лимит на весь HTTP-запрос, сек |
| `CMD_TIMEOUT` | 20 (1–120) | Таймаут команды реле, сек |
| `CMD_MEM_MB` | 512 (64–4096) | Лимит памяти дочерней команды |
| `MAX_RSS_MB` | 80 (20–2048) | Лимит памяти сервиса; при превышении он перезапускается |
| `MAX_ON_SECONDS` | 60 (1–600) | Максимум времени ON в паттерне (защита от опечаток) |
| `MAX_PULSE_COUNT` | 30 (1–100) | Максимум импульсов в паттерне |
| `STATE_MAX_AGE` | 3600 (0–86400) | Сколько секунд считать сохранённое состояние актуальным; `0` — не восстанавливать |
| `LOG_FILE` | — | Дублировать лог в файл, например `/var/log/alarm/alarm.log` |
| `LOG_MAX_MB`, `LOG_BACKUPS` | 5, 5 | Ротация файла лога |
| `LOG_ALERT_DATA` | 0 | `1` — писать в лог сырой ответ API во время тревоги (строки `[DATA]`) |
| `LOG_DATA_MAX` | 4000 | Максимальная длина записи сырых данных |

Паттерн, не прошедший проверку (опечатка, превышение лимитов), пропускается с
предупреждением. Ошибка в обязательных параметрах останавливает сервис с кодом 78.

## Защита от зависаний и перерасхода памяти

- **Watchdog systemd** (`Type=notify`, `WatchdogSec=120`): сервис сообщает о
  работоспособности раз в секунду; при зависании systemd его перезапускает.
- **Таймауты везде**: HTTP (на операцию и жёсткий дедлайн на весь запрос),
  команды реле (с уничтожением всей группы процессов), жизнь процесса `on|off` — 30 с.
- **Память**: самоконтроль RSS (`MAX_RSS_MB`), лимит ответа API 1 МиБ, лимит
  памяти дочерних команд, cgroup-лимиты (`MemoryHigh=100M`, `MemoryMax=128M`,
  `TasksMax=32`, `CPUQuota=50%`).
- **Реле не остаётся включённым**: выключение с повторами в `finally`, при
  остановке и падении — `ExecStopPost`.
- **Ошибки API**: повторы с нарастающей паузой, проверка структуры ответа.
- **Изоляция**: отдельный пользователь, `ProtectSystem=strict`,
  `NoNewPrivileges`, ограничение сетевых семейств и др.

## Эксплуатация

```bash
systemctl status alarm            # состояние
journalctl -fu alarm              # лог в реальном времени
systemctl restart alarm           # после правки config.txt
sudo -u alarm /opt/alarm/venv/bin/python /opt/alarm/alarm.py check
sudo -u alarm /opt/alarm/venv/bin/python /opt/alarm/alarm.py on|off
sudo /opt/alarm/venv/bin/pip install -U tinytuya && sudo systemctl restart alarm
```

В обычном режиме лог молчит, пока ничего не происходит. Это нормально:
записи появляются при старте, тревоге, смене типа, отбое и ошибках.

## Диагностика

| Симптом | Что делать |
|---|---|
| `id: 'alarm': no such user`, `invalid group 'alarm'` | Запускайте установку как `sudo bash install.sh` (не `sh`) |
| `Не удалось импортировать tinytuya` | Проверьте `requirements.txt` и venv: `/opt/alarm/venv/bin/pip list`; затем `alarm.py check` — он покажет настоящую причину |
| Сервис завершился с кодом 78 | Ошибка конфигурации или `snapshot.json`; причина в `journalctl -u alarm` |
| Реле не срабатывает, ошибки сети | Проверьте IP реле в `snapshot.json` (лучше закрепить за ним статический адрес в DHCP) |
| Жёлтая тревога распознаётся как обычная `AIR` | Включите `LOG_ALERT_DATA=1` и посмотрите строки `[DATA]` во время тревоги |

## Известные ограничения

- Структура уровней воздушной тревоги (`activeAlertLevels` и названия
  `RED`/`ORANGE`/`YELLOW`) поддерживается по реальным ответам API ukrainealarm
  (ключ `alertLevel`). Если уровень отсутствует в ответе, тип считается `AIR`
  (общая тревога). Для отладки сырых данных служит `LOG_ALERT_DATA=1`.
- Пока идёт паттерн, опрос API приостановлен; изменение статуса в это время
  будет обработано после его завершения.
- При остановке сервиса реле просто выключается, паттерн отбоя не проигрывается.
  Состояние старше `STATE_MAX_AGE` не восстанавливается.
- `CMD_ON`/`CMD_OFF` выполняются через shell, как в исходном скрипте, поэтому
  `config.txt` считается доверенным (права `640`, владелец root:alarm).
- Проверка сети до реле при старте не выполняется (только чтение `snapshot.json`).

## История изменений

**1.0.2** (форк/модернизация) — исправлено определение уровня (цвета) тревоги:
  API ukrainealarm возвращает уровень в ключе `alertLevel`, а не `level`.
  Красная/оранжевая/жёлтая тревога теперь определяются как `AIR_RED` /
  `AIR_ORANGE` / `AIR_YELLOW` вместо общей `AIR`. Добавлены unit-тесты.
  Если уровень отсутствует в ответе API — используется общая тревога `AIR`.
**1.0.1** — проект лицензирован: GNU General Public License v2.0 (GPL-2.0-only), добавлен файл `LICENSE`,
в файлы — заголовки `SPDX-License-Identifier` и копирайт.

**1.0.0** — первая сводная версия. Относительно исходных `alarm.py` и `on.py`:

- всё объединено в один файл, управление реле встроено (`on` / `off` / `check`),
  `on.py` больше не нужен; формат `config.txt` сохранён;
- запуск как сервис из venv под systemd, установочный скрипт;
- таймауты, watchdog, контроль памяти, лимиты, гарантированное выключение реле;
- реакция на смену типа тревоги (жёлтая ↔ оранжевая ↔ красная ↔ `AIR`);
- уровень `AIR_ORANGE`, неопределённая воздушная тревога как `AIR`;
- сохранение состояния между перезапусками;
- ограничения на паттерны, ретраи и backoff при ошибках API;
- опциональный лог в файл с ротацией и отладочный вывод сырых данных API;
- проверка `snapshot.json` и `tinytuya` при старте, режим диагностики `check`;
- ID реле больше не зашит в код (`TUYA_DEVICE_ID` или единственное устройство в snapshot).
